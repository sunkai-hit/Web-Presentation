# Wish-to-Reality Web PPT Content & Visual Rules v2.1

本规则只适用于 `projects/wish-to-reality-reading/` 项目，不影响仓库其他项目。

## 0. 强制验收顺序

任何新版本必须按以下顺序执行，不能跳步：

1. **内容稿逐页确认**：确认每一页内容稿都达到已确认 demo 的完整度。
2. **页面实现逐页确认**：确认每一页 HTML 都按“电影院陈爆米花实验页”的完整度实现，没有把内容稿压缩成摘要卡片。
3. **视觉检查**：只有前两项逐页确认无误后，才允许进入视觉 QA。

如果第 1 或第 2 项任一页 FAIL，必须先返工该页，不能进入最终视觉检查。

## 1. 内容基线不可降级

用户确认过的前 1–6 页详细文案，以及“电影院陈爆米花实验”测试页，是本项目的 Canonical Content Baseline。任何后续版本不得通过摘要、改写、自动切片、自动卡片化等方式降低其信息量和解释完整度。

## 2. 完整内容稿定义

完整内容稿不是大纲，不允许用“本页介绍……”“这一页讲……”代替真实正文。主体页必须实际写出：核心问题、背景/前提、主要解释、故事或例子、机制、作者观点/现代解释、页面结论。

每页内容稿必须能回答：

- 这一页的完整问题是什么？
- 第一次接触的人需要知道哪些背景？
- 作者或研究真正想说明什么？
- 有什么故事、实验、例子或生活迁移？
- 现代解释和边界是什么？
- 这一页最终落到哪一句结论？

## 3. HTML 必须逐页映射

禁止使用通用 parser 将 Markdown 正则拆成卡片后自动生成页面。每页布局必须按该页内容单独组织，明确哪些文字是主区、哪些做图示、哪些做表格、哪些放页底结论。

页面实现不能只复述内容稿的标题或摘要，必须覆盖该页的 Required Blocks。

## 4. 内容覆盖检查

每页先列出 Required Blocks。HTML 缺失任一必要块，直接 FAIL。以爆米花页为例，必须包含：研究问题、实验场景、实验设计、强/弱习惯、新鲜/陈爆米花、结果矩阵、为什么重要、生活迁移、页底结论。

## 5. 页面实现完整度检查

每一页 HTML 必须检查：

- 是否覆盖内容稿 Required Blocks；
- 是否保留故事 / 实验 / 机制 / 现代解释，而不是只留下概括句；
- 是否至少有一个有信息承载的图示、流程、矩阵、对照、场景或图标组；
- 是否存在“大面积容器 + 极少文字”的空框；
- 是否比 Canonical Baseline 变薄。

## 6. 视觉 QA 是第三关

第一关检查内容稿是否达标；第二关检查 HTML 是否完整实现内容；第三关才检查溢出、边界、对齐、字号、空容器、页面利用率和阅读顺序。

## 7. 视觉红线

- 正文原则上不低于 17–18px 的投屏等效可读度；
- 不允许为了塞内容将主体文字压到不可读；
- 面积超过页面 15% 的容器，不允许只有标题 + 1–2 行正文；
- 主体知识页视觉占用率应约 65%–85%；
- 宁可重排或拆页，不允许放大空框。

## 8. 回归测试页

每次提交必须检查：第 2 页 Manifestation、第 5 页十章地图、第 6 页 Shinn 机制、爆米花实验页、WOOP 页、最终整合页。任何一页比基准内容变薄，不能发布。

## 9. QA 记录要求

每个版本必须在 `.project/qa-vX.Y.Z.md` 记录三段结果：

1. 内容稿逐页确认表；
2. 页面实现逐页确认表；
3. 视觉检查结果。

如果前两段未全部 PASS，第三段不得填写为最终视觉通过。
